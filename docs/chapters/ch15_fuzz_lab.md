# 協定解析器 Fuzz 測試實驗室（Protocol Parser Fuzz Lab）

## 這個頁面在做什麼？

在真實嵌入式與伺服器運作環境中，實體通訊匯流排（如 I2C、SPI、UART、PCIe）常面臨各種非理想因素，例如電源瞬斷、電磁雜訊干擾、電平浮接、熱插拔抖動或 DMA 緩衝區溢位。這些狀況導致邏輯分析儀或系統日誌擷取到的資料常包含截斷字元、格式錯位、非預期的特殊符號（如 invalid、NaN、負數或極大數值）或破損封包。

若診斷工具或 BMC 韌體解析器（Parser）未做好嚴謹的輸入防禦與邊界檢查，在讀取這些畸形資料時拋出未處理例外（Unhandled Exception，例如 IndexError、KeyError、ZeroDivisionError、AttributeError），可能導致整個除錯介面崩潰甚至引發系統守護行程（Daemon）終止。

**協定解析器 Fuzz 測試實驗室（Fuzz Lab）** 提供專用的模糊測試（Fuzzing）與穩健性（Robustness）壓力測試環境，支援五大常見協定輸入：

- **I2C 匯流排 CSV（I2C Decoded CSV）**
- **SPI Flash 匯流排 CSV（SPI CSV）**
- **PCIe lspci 設定空間（PCIe lspci Output）**
- **UART 崩潰日誌（UART Crash Log）**
- **原始十六進位傾印（Raw Hex Dump）**

透過自動化產生邊界與畸形輸入衝擊解析引擎，量化評估解析器的防禦攔截能力，確保在任何惡意或極端格式下均能優雅處理。

## 怎麼操作？

進入 GUI 側邊欄 **「實驗室與學習」** 區塊的 **「🎲 協定解析器 Fuzz 測試」** 頁面。頂部設有兩個獨立分頁：

### 分頁一：🔬 單次 Fuzz 產生與即時分析

1. **選擇目標協定（Target Protocol）**：從下拉選單選擇欲測試的協定（I2C、SPI、PCIe、UART 或 Raw Hex Dump）。
2. **隨機種子配置（Seed Configuration）**：
   - **隨機模式**：預設不勾選「指定隨機種子」，每次點擊均產生全然隨機之測試資料。
   - **決定性種子（Deterministic Seed）**：勾選後輸入指定整數（例如 42），可精準重現特定邊界輸入。
3. **資料規模控制（Row / Line Count）**：滑動調整資料筆數（5 ~ 200 行；PCIe 固定為 256B 設定空間，UART 自動產生完整 Panic/HardFault 結構）。
4. **產生與下載**：
   - 點擊 **「🎲 產生 Fuzz 測試資料」**，上方代碼框即時顯示產生的隨機內容。
   - 點擊 **「💾 下載此 Fuzz 測試資料」** 可保存為本機測試檔案（.csv、.txt 或 .log）。
5. **即時解析結果**：下方即時顯示解析器狀態判定（解析成功、輸入驗證攔截或未預期崩潰）與詳細指標卡片。

### 分頁二：⚡ 批次壓力測試與統計

1. **配置批次參數**：
   - **測試目標協定**：可選擇「全部協定混合測試（All Protocols）」或指定單一協定。
   - **執行次數（Iterations）**：可選 10、20、50、100 或 200 次。
   - **起始隨機種子（Base Seed）**：指定基礎種子編號（依序遞增測試）。
2. **啟動測試**：點擊 **「🚀 啟動批次 Fuzz 壓力測試」**，系統將以高速並行循環衝擊解析器，並呈現動態進度條。
3. **檢視統計報表**：
   - 查看四項頂部 KPI：總測試次數、解析成功率（Parsed OK）、輸入驗證攔截率（Handled Error）與未預期崩潰率（Unhandled Crash）。
   - 展開「檢視完整測試歷程紀錄」表格，審視每一筆測試的協定、種子與詳細摘要。

## GUI 會顯示哪些輸出？

| 畫面區段 | 顯示內容 | 判定意義與除錯重點 |
|---|---|---|
| Fuzz 測試資料檢視器 | 即時產生的 CSV、文字或十六進位隨機內容 | 直觀檢驗注入之畸形欄位（如非法字串、缺失欄位、超出範圍的十六進位） |
| 單次解析狀態橫幅 | 綠色（Parsed OK）、黃色（Handled Error）或紅色（Unhandled Crash） | 評估解析器對當前邊界資料之防禦行為 |
| 詳細解析指標卡片 | 依協定提取之關鍵欄位（如交易數、異常數、裝置 BDF、崩潰類型等） | 確認在有效結構下解析器是否能精準提取協定欄位 |
| 批次測試 KPI 指標 | 總測試次數、成功率百分比、攔截率百分比、崩潰次數與平均耗時 | 量化軟體 Robustness 品質，作為 CI/CD 綠燈發布之依據 |
| 批次歷程資料表 | 每一輪測試的編號、協定、Seed、狀態圖示與詳細摘要 | 定位發生崩潰之特定 Seed，便於後續單元測試重現與修復 |

### 三種結果判定標準（Outcome Statuses）

- **✅ 解析成功（Parsed OK / Success）**：
  - 說明：輸入資料雖包含隨機雜訊或非典型時序，但結構符合協定基礎要求，解析器成功解碼並回傳報告。
- **🛡️ 輸入驗證攔截（Handled Error）**：
  - 說明：輸入資料存在嚴重畸形（如無效十六進位字元、時間倒退、缺少必要欄位等），解析器在邊界處主動捕捉並拋出明確的已知例外（如 ValueError、KeyError、TypeError），優雅拒絕檔案。這是良好的防禦性程式設計（Defensive Programming）表現。
- **🚨 未預期崩潰（Unhandled Crash）**：
  - 說明：解析器發生未捕捉的內部例外（如 IndexError: list index out of range 或 AttributeError: 'NoneType' object has no attribute），導致程式崩潰。此情況被判定為軟體缺陷，必須加以修補。

### 各協定解析器提取指標對照

| 測試協定 | 核心解析器 | 正常解析時提取之關鍵指標 |
|---|---|---|
| **I2C Decoded CSV** | I2CDiagnosticEngine | 總交易數（Total Transactions）、異常事件數、偵測裝置位址數、資料品質警告數 |
| **SPI CSV** | SPIDiagnosticEngine | 總交易數、異常事件數、資料品質警告數 |
| **PCIe lspci** | PCIeAnalyzer | 匯流排編號 (BDF)、廠商 ID (Vendor ID)、裝置 ID (Device ID)、類別名稱、標準能力數 (Caps) |
| **UART Crash Log** | UARTCrashParser | 崩潰類型 (Crash Type：Kernel Panic / HardFault 等)、摘要標題、原始日誌行數 |
| **Raw Hex Dump** | 內建驗證器 | 總行數、總位元組數、非零位元組數、零值位元組數 |

## 證據等級邊界（Evidence Level & Limitations）

進行 Fuzz 測試與閱讀報告時，應明確以下證據邊界：

- **合成模糊測試資料（Synthetic Malformed Data）**：Fuzz 產生的資料是由亂數產生器（random.Random）合成之測試向量，非真實目標系統之硬體擷取檔。
- **不能證明完整協定合規性（Protocol Conformance）**：Fuzz 測試主要驗證解析器的「穩健性（不崩潰）」與「防禦攔截」，無法替代針對 PCI-SIG、I2C Specification 或 JEDEC 官方標準的一致性認證測試。
- **批次 100% 成功之統計意義**：批次測試未發現崩潰，代表解析器在「該隨機分佈與種子空間內」具備高度穩健性，但不代表已涵蓋數學意義上的所有輸入排列組合。
- **UART 日誌僅供格式解析驗證**：Fuzz 產生的 Linux Call Trace 或 ARM 暫存器傾印為合成日誌，不可用於特定板卡的真實當機原因診斷。

## 實際場景範例

### 場景 1：防範邏輯分析儀匯出檔包含 NaN 與非法字串

**背景**：某廠牌邏輯分析儀在訊號嚴重雜訊時，匯出的 CSV 欄位可能包含 NaN、invalid 或 0xFFFFFFFFFF 等非預期字串。  
**驗證過程**：
1. 在單次 Fuzz 頁面中選擇「I2C 匯流排 CSV」，產生包含隨機 invalid 與 NaN 的測試資料。
2. 檢視下方解析結果：系統顯示「🛡️ 【輸入驗證攔截 (Handled Error)】輸入驗證攔截：Invalid address or format」。
3. 證明 I2C 解析器已具備嚴謹的型別檢查，不會因異常字串引發轉型崩潰。

### 場景 2：CI/CD 整合 100 次混合批次壓力測試

**背景**：團隊在發布診斷工具新版本前，需要確保重構後的協定解析核心無任何潛在的未處理例外。  
**驗證過程**：
1. 在批次 Fuzz 頁面選擇「全部協定混合測試」，執行次數設為 100 次（5 種協定共 500 次測試），Base Seed 設為 0。
2. 啟動測試，大約 1.5 秒內完成 500 次解析衝擊。
3. 統計結果顯示：總測試 500 次，解析成功 210 次（42.0%），輸入防禦攔截 290 次（58.0%），未預期崩潰 0 次（0.0%）。
4. 綠燈確認解析核心具備極佳的 Robustness，符合發布標準。

### 場景 3：利用固定種子（Deterministic Seed）重現與修復邊界 Bug

**背景**：自動化測試回報在特定極端資料下 PCIe 解析器發生異常。  
**驗證過程**：
1. 勾選「指定隨機種子」並輸入測試報告中的 Seed=1024，系統精準還原產生當時引發異常的 256-byte lspci 傾印。
2. 開發人員可在此頁面即時觀察解析器的報錯行號與變數狀態，修補例外處理邏輯後重新點擊分析，驗證狀態由「🚨 未預期崩潰」轉為「🛡️ 防禦攔截」。
