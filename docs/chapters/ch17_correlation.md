# Ch17 — 跨協定時間線關聯分析

## 適用場景

在複雜嵌入式系統、伺服器主機板與 BMC（Baseboard Management Controller）環境中，許多棘手的硬體與韌體故障並非單一通訊協定（Single Protocol）所能完全解釋。單獨觀察某一匯流排時，往往只能看見「症狀」而非「根因（Root Cause）」。

以下為典型的跨協定關聯分析適用場景：

- **系統級連鎖故障（Cascading Failures）**：當底層硬體或電源出現異常時，通常會骨牌式引發多條匯流排連續出錯（例如電源驟降先引發 I2C 存取 NACK，接著 SPI Flash 寫入超時，最後驅動層崩潰觸發 UART Panic）。
- **I2C NACK 與 SPI 寫入失敗同時出現**：例如 3.3V 或 1.8V 共同電源軌暫態跳變（Power Rail Glitch / Droop），導致掛在同一電源下的 I2C 感測器與 SPI NOR Flash 同步發生通訊中斷。
- **電源異常或熱插拔造成的總線突波**：熱插拔 PCIe 介面卡或風扇模組時產生電磁干擾（EMI）或電壓下陷，造成多個不同介面的封包同一瞬間 CRC 錯誤或逾時。
- **BMC 異常重置（Watchdog / Brown-out Reset）**：BMC 或 MCU 在突發重置前夕，I2C、SPI 與 UART 串列埠在數毫秒（ms）內同時出現傳輸中斷、亂碼或未完成的交易。

透過將多協定追蹤（Trace）資料對齊至單一時間軸，工程師可直觀判斷事件發生的先後順序，釐清「因果關係」，避免在次要症狀上浪費除錯時間。

## 操作步驟

### Step 1: 準備多協定追蹤資料

在進行跨協定分析前，需先從邏輯分析儀、匯流排側錄器或系統終端擷取相關資料（各協定資料需具備時間戳欄位以供對齊）：

1. **I2C / PMBus Decoded CSV**：邏輯分析儀（如 Saleae Logic）匯出的 I2C 解碼 CSV，需包含 `Time [s]`、`Packet ID`、`Address`、`Data`、`Read/Write`、`ACK/NAK` 等欄位（亦支援文字 trace 格式）。
2. **SPI Flash Decoded CSV**：包含 `Time [s]`、`MOSI`、`MISO`、`CS` 等解碼資料，涵蓋 Opcode（如 0x06 WREN、0x02 PP、0x05 RDSR）與時間戳。
3. **UART Crash Log**：串列埠終端記錄的 Linux Kernel Panic、Call Trace、Oops 或 ARM Cortex-M HardFault 傾印日誌（.log / .txt）。

### Step 2: 上傳至關聯分析頁面

1. 啟動 Web 介面並切換至側邊欄 **「進階分析」** 區塊的 **「🔗 跨協定時間線關聯分析」** 頁面。
2. 在 **「📂 上傳追蹤資料」** 區域，分別提供三組輸入（可上傳檔案或直接貼上文字內容，至少需提供一組）：
    - **左欄（I2C / PMBus CSV）**：上傳 I2C 解碼 CSV 或貼上內容，解析成功後會顯示交易筆數。
    - **中欄（SPI Flash CSV）**：上傳 SPI 解碼 CSV 或貼上內容，解析成功後會顯示操作筆數。
    - **右欄（UART Crash Log）**：上傳系統崩潰日誌或貼上文字，解析成功後會標註識別到的崩潰類型。

### Step 3: 解讀時間線圖表

資料上傳並解析後，系統會自動在下方繪製 **「📈 跨協定時間線」**（Plotly 互動式散佈圖）：

1. 觀察整體事件在時間軸（毫秒，ms）上的分佈狀況。
2. 頂部 KPI 指標卡片會即時呈現：
    - **總事件數（Total Events）**：所有協定事件加總。
    - **異常事件（Anomaly Count）**：被判定為錯誤、NACK 或崩潰的事件總數。
    - **涵蓋協定（Protocols Seen）**：目前時間線上包含的協定類型（I2C、SPI、UART）。
3. 將滑鼠懸停於圖表上的資料點，檢視具體時間戳（Time in ms）、協定名稱與事件標籤。

### Step 4: 異常叢集分析

1. 滾動至 **「🔗 跨協定異常叢集偵測」** 區塊。
2. 調整 **「叢集時間窗口 (ms)」** 滑桿（預設 2.0 ms，範圍 0.1 ~ 50.0 ms）。
3. 當系統偵測到在指定時間窗口內，有涵蓋 2 種以上協定的異常事件同時或相繼發生，將自動歸類為一個「異常叢集（Cluster）」。
4. 展開叢集詳細卡片，檢視涉及協定、事件摘要與共同根因推論。

## 圖表判讀

### 時間線圖表

```
Y 軸（協定通道）
  ▲
  │   I2C   ●   ●   ●   ★ (I2C NACK @ 12.450 ms)
  │                      
  │   SPI       ●   ●   ★ (SPI Status Error @ 12.480 ms)
  │                      
  │  UART               ★ (Kernel Panic @ 12.500 ms)
  └────────────────────────────────────────────────────────► X 軸：時間 (ms)
      圖例： ● 正常事件（圓點）   ★ 異常事件（紅色星號）
```

- **X 軸（時間，ms）**：以毫秒為單位的統一時間基準線。所有協定的 timestamp（秒）均轉換為毫秒對齊顯示。
- **Y 軸（協定通道）**：分層排列三大通訊協定：
    - **頂層（Y=3，天空藍 `#0ea5e9`）**：I2C 匯流排事件（包含正常 Transaction 與 NACK / Timeout / Clock Stretch 異常）。
    - **中層（Y=2，紫色 `#a855f7`）**：SPI Flash 匯流排事件（包含正常 Opcode 讀寫與 Status Register Error / WREN 缺失異常）。
    - **底層（Y=1，橘色 `#f97316`）**：UART 串列日誌事件（包含 Kernel Panic、Oops、HardFault 等系統崩潰事件）。
- **標記符號（Markers）**：
    - **圓點（Circle，小尺寸）**：正常傳輸事件（如 `I2C Txn 0x50`、`SPI 0x03`）。
    - **紅色星號（Red Star `#ef4444`，大尺寸）**：異常事件（如 `I2C NACK on 0x58`、`SPI Flash Busy Timeout`、`UART Crash: Kernel Panic`）。

### 叢集分析表

叢集分析引擎透過滑動窗口演算法，自動辨識在極短時間差內跨多個通道爆發的複合性異常：

| 介面欄位 / 控制項 | 功能說明 | 除錯判讀重點 |
|---|---|---|
| **叢集時間窗口滑桿 (0.1 ~ 50.0 ms)** | 定義判定多事件屬於同一叢集的時間差閾值 | 若系統為電源暫態擾動，通常時間差在 1~5 ms 內；若是軟體逾時連鎖反應，可放寬至 10~50 ms 觀察。 |
| **涉及協定（Protocols）** | 該叢集跨越的協定清單（例如 `I2C, SPI` 或 `I2C, SPI, UART`） | 跨越的協定種類越多，代表問題越接近全域層級（如電源、重置線或共享 Clock）。 |
| **事件摘要（Summary）** | 叢集內各異常事件之標籤串接 | 觀察事件串列的排列順序，排在最前面的事件往往是引發後續崩潰的第一現場。 |
| **可能意義與根因建議** | 系統針對多協定併發異常之推論提示 | 提示工程師優先量測供電電壓、檢查共用 Reset/Power-Good 線路，而非單獨修改某一匯流排的驅動程式。 |
| **事件明細表格（Event Table）** | 條列包含協定、時間 (ms)、事件說明、異常布林值之清單 | 提供完整的精確數據對照，便於匯出作為 Formal RCA 報告之佐證。 |

## 真實排查案例

### 案例 1: 電源跳變造成 I2C NACK + SPI Status Error

#### 1. 故障現象與情境
某伺服器主機板在執行負載壓力測試時，BMC 隨機回報溫控晶片（LM75，I2C 0x48）讀取失敗，同時 BIOS SPI Flash 更新作業中斷。單獨檢查 I2C 驅動日誌顯示 `i2c-trans: NACK received`；單獨檢查 SPI 驅動日誌則顯示 `spi-nor: write status register timeout`。兩邊的軟體工程師各自懷疑對方匯流排佔用 CPU 資源或 Lock contention。

#### 2. 跨協定診斷操作
1. 使用 8 通道邏輯分析儀同時擷取 I2C SCL/SDA 與 SPI CS/CLK/MOSI/MISO 訊號。
2. 匯出 I2C Decoded CSV 與 SPI Decoded CSV。
3. 上傳至本工具「跨協定時間線關聯分析」頁面。
4. 設定叢集時間窗口為 `2.0 ms`。

#### 3. 圖表判讀與根因分析
- **時間線觀察**：
    - 在 `t = 345.120 ms` 時，I2C 通道出現紅色星號 `I2C NACK on 0x48`。
    - 在 `t = 345.210 ms` 時，SPI 通道出現紅色星號 `SPI Write Error: WIP Timeout`。
    - 兩者時間差僅 **0.090 ms（90 µs）**。
- **叢集偵測報告**：系統標記叢集 `#1` 涉及 `I2C, SPI`，事件摘要為 `I2C NACK on 0x48 + SPI Write Error`。
- **硬體實體查證**：兩事件在 90 µs 內同時發生，軟體排程無法在如此短時間內引發跨匯流排連鎖。工程師以示波器勾測板上 3.3V 輔助電源（3V3_AUX），發現當主電源進行 VRM 相位切換時，3V3_AUX 出現高達 600 mV 的電壓驟降（Voltage Droop），導致 LM75 與 SPI Flash 同時低於最低工作電壓而停止回應。
- **處置方案**：在 3V3_AUX 軌上補充電源去耦電容（Decoupling Capacitor），問題徹底解決，證實非軟體驅動缺陷。

### 案例 2: BMC 重置造成三協定同時中斷

#### 1. 故障現象與情境
系統運作中無預警出現全機離線，重啟後作業系統 dmesg 留下 Kernel Panic，但 panic 前夕各周邊感測器均回報通訊超時。

#### 2. 跨協定診斷操作
1. 收集 BMC 崩潰前的 I2C 監控日誌、SPI 通訊 CSV 以及串列埠 UART 終端日誌。
2. 將三者分別載入跨協定關聯分析頁面。

#### 3. 圖表判讀與分析
- **時間線對齊**：
    - `t = 1200.000 ms`：I2C 匯流排正在傳輸感測器數據，突然終止於 mid-byte 並出現 SCL 低電平逾時。
    - `t = 1200.000 ms`：SPI Flash CS 拉高且傳輸中斷。
    - `t = 1200.000 ms`：UART 記錄到 `Watchdog bark! System Resetting...` 隨後觸發 Kernel Panic。
- **結論**：三協定異常事件於同一基準點（`t = 0` 相對時間）爆發，確認為 BMC Watchdog 硬體重置（L1 物理層事件）導致所有通訊介面同步歸零，排除了個別周邊晶片損壞的假說。

## 限制與邊界

使用跨協定時間線關聯分析工具時，請務必掌握以下邊界條件：

- **時間對齊依賴各協定追蹤的 Timestamp 欄位**：
    - 若各協定資料來自同一台多通道邏輯分析儀（共享同一硬體採樣時鐘），時間對齊精準度可達微秒（µs）至奈秒（ns）級。
    - 若資料來自不同獨立擷取設備，必須手動確保各檔案具備共同的時間基準點；否則時間軸上的相對位置可能存在系統偏移（Clock Drift / Offset）。
- **UART Log 通常無精確微秒時間戳**：
    - UART 日誌（如純文字 console log 或 dmesg）常缺少硬體取樣級的精確時間戳，工具預設將 UART 崩潰事件置於時間基準點（`t = 0.0 ms`）。
    - 當結合 UART 進行分析時，需搭配日誌內記載的系統 uptime 或相鄰協定事件進行人工相對時間校對。
- **叢集偵測採用時間窗口啟發式聚類，不做因果推斷**：
  - 叢集分析僅代表多個異常事件在「時間維度相近」（Correlation），**不等於自動證明先發生的事件必定是後發生事件的物理根因（Causation）**。
  - 軟體分析報告為縮小排查範圍之指引，最終判定仍需對照原理圖（Schematic）、示波器電源波形與硬體暫存器狀態。
