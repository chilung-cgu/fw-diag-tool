# v1.6.0 Comprehensive Enhancement — Design Spec

> **Created via:** superpowers:brainstorming (Architectural path)
> **Date:** 2026-08-30
> **Baseline:** v1.5.0 (23a7441, 1034 tests, 78.55% coverage)

## Problem Statement

After v1.5.0 sealed CLI diff symmetry, correlation expansion, session export,
diff JSON, i18n audit, and dashboard enhancements, deep analysis reveals three
systemic gaps that limit the tool's professional maturity:

1. **Coverage gap**: 78.55% branch coverage, below the configured 80% fail_under
   gate. Key under-covered modules: gui/ pages (heavily mocked but not all branches),
   reporting/ (pdf_report 88%, spi/reporter 78%, uart/reporter 85%),
   session/session_manager (82%).

2. **Protocol engine maturity imbalance**: I2C has 10,512 lines across 14 modules
   with dedicated timing analysis, waveform diff, chip database, raw capture,
   sensor decoders, MUX tracker, and EEPROM support. Other protocols are
   significantly thinner:
   - PCIe: 2,049 lines (7 modules) -- no timing analysis, no link training timeline
   - SPI: 2,107 lines (8 modules) -- no command latency stats, no throughput metrics
   - UART: 1,044 lines (5 modules) -- no baud rate detection, no timing breakdown
   - MCTP: 1,216 lines (5 modules) -- no response time analysis, no session stats

3. **Reporting and export fragmentation**: HTML/PDF generators exist but only I2C
   has deep integration. Multi-protocol unified reports, CSV data export for
   analysis results, and comparative multi-session reports are missing.

## Design Goals

### G1: Test Coverage to 85%+ (from 78.55%)
Close branch coverage gaps in reporting/, session/, gui/ pages, and protocol
reporters. Add integration tests that exercise real parse-analyze-report-export
pipelines end-to-end.

### G2: Protocol Engine Timing and Statistics Modules
Add lightweight timing/statistics analysis to SPI, UART, PCIe, and MCTP engines,
bringing them closer to I2C's maturity level. Each gets:
- A timing.py or statistics.py module with protocol-appropriate metrics
- Integration into existing reporters and GUI pages
- CLI summary output

### G3: Unified Multi-Protocol Report Generator
Create a single-entry-point report builder that combines results from any
combination of protocols into one unified HTML or Markdown document, suitable
for firmware QA sign-off sheets.

### G4: CSV Data Export for All Protocol Results
Every protocol analysis result can be exported as CSV, enabling engineers to
import data into Excel/Sheets for custom analysis.

### G2: Protocol Timing/Statistics Modules

SPI Statistics (src/fw_diag_tool/spi/statistics.py):
- Command frequency distribution (READ/WRITE/ERASE/STATUS counts)
- Average command-to-command latency (when timestamps available)
- Throughput estimate: total bytes transferred / trace duration
- BUSY poll count and average wait duration
- Page program cycle time statistics

UART Timing (src/fw_diag_tool/uart/timing.py):
- Baud rate detection from inter-character timing
- Character-to-character latency histogram
- Boot sequence phase timing (bootloader -> kernel -> userspace)
- Crash-to-reset interval measurement

PCIe Statistics (src/fw_diag_tool/pcie/statistics.py):
- Link training completion time (from dmesg timestamps)
- AER error rate (errors per time window)
- Multi-device topology summary statistics
- Config space read latency (if timestamps available)

MCTP Statistics (src/fw_diag_tool/mctp/statistics.py):
- Request-response round-trip time
- Message reassembly success rate
- EID communication matrix (who talks to whom)
- Error rate by message type

Each module:
- Returns a frozen dataclass result
- Integrates into the existing reporter's Markdown output
- Feeds a new "Statistics" expander in the GUI page
- Has dedicated unit tests

### G3: Unified Multi-Protocol Report

Module: src/fw_diag_tool/reporting/unified_report.py

Takes a list of per-protocol analysis results and produces:
- Combined executive summary with cross-protocol health score
- Per-protocol sections with consistent structure
- Cross-protocol anomaly correlation summary
- Sign-off checklist with pass/fail gates

Integration:
- New GUI page: unified_report_ui.py -- multi-file upload, combined report preview
- CLI: fw-diag report subcommand accepting multiple input files
- i18n: All new text keys registered in gui.py domain

### G4: CSV Data Export

Module: src/fw_diag_tool/reporting/csv_export.py

Generic CSV serializer that accepts any protocol's result dataclass and
flattens it into rows/columns:
- I2C: one row per transaction (address, R/W, data, ACK/NACK, timing, anomalies)
- SPI: one row per command (opcode, address, data length, status, timing)
- UART: one row per log line or crash frame
- PCIe: one row per device or per AER error
- MCTP: one row per packet/message or per IPMB frame

Integration:
- Download button on every protocol GUI page
- CLI: --format csv option on analyze subcommands
- Consistent UTF-8 BOM for Excel compatibility

## Testing Strategy

- Each new module has its own test file with >= 10 tests
- Integration tests exercise full pipelines: file input -> parse -> analyze -> report -> export
- Coverage target: 85%+ overall, 90%+ for new modules
- All existing 1034 tests must continue passing
- Benchmarks must not regress (protocol engine parse times within 20%)

## Risk Assessment

- Low risk: CSV export, coverage tests -- additive with no behavioral change
- Medium risk: Timing/statistics modules -- must handle missing timestamps gracefully
  (many trace formats lack precise timing data)
- Medium risk: Unified report -- aggregation logic must handle partial results
  (e.g., only I2C and PCIe provided, not all 5 protocols)
- Mitigation: All timing modules return "unavailable" metrics when source data
  lacks timestamps, using the existing EvidenceMetric pattern
